### Feature

**You own the design. Plan, review, verify.** Delegate implementation. Stay in the lead.

1. Trace the affected subsystem.
2. `architect` for the shape.
3. Write the throughput checkpoint as four todo items. A dimension that genuinely does not apply (single file, no fan-out) keeps its item with `n/a: <reason>` rather than being dropped:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize.
   - **Shared mutable state.** Default to splitting the target (the **separate-before-serializing-shared-state** principle skill). Serialize only for real invariants.
   - **Smallest safe decomposition.** If one worker is best, name why.
4. Pin the checks before implementation. Give an `impl` worker the chosen design and [check table template](../../bstack-feature/references/template/checks.md). For each applicable PRD row, fill in `.bstack/<name>/checks.md` and prepare the checks it names without changing production code. Put execution results in the worker report, not the table; do not request a design write-up, baseline report, or test inventory. Read the table, commit it with any test changes, and record the check SHA.
5. Delegate code-writing to `bstack-run run --role impl --brief "$BRIEF"` with a specific scope (file paths, named data shape and its organizing structure per **principle-model-the-domain**, a state machine over scattered booleans, a table/registry over branching, a typed model over repeated shape assumptions, chosen before the delegate writes logic, and success criteria). When the implementation admits multiple valid shapes (error handling, abstraction layer, test structure), delegate via the **arena** skill instead so the runners surface the alternatives and the cross-judge guards the pick. Mandatory: no skip-with-reason escape, and Laziness Protocol does not override it (the gain is review separation, not lines saved). An implementation worker owns its scoped diff directly; the coordinator assigns the independent review. Surgical edits, re-ground against the source for upstream-derived files. Port shared-primitive improvements to all consumers and verify each. Commit liberally.
   Before delegating implementation of a new feature, require the current approved PRD unless the user explicitly waived it. Give the worker the approved index, review run ID and applicable `F-xx/성공 정의` cells, and the PRD's 정책 section (policies to keep or change), plus the check SHA and `checks.md`. The work is done when every row's 검증 방법 passes. The worker does not edit the check table or its tests; `git diff <check SHA> HEAD -- .bstack/<name>/checks.md <test paths>` stays empty. A worker that finds a check wrong stops and reports. Changing the check table or its tests is a user decision (step 7), then pin a new check SHA. If waived, include the user's waiver and the agreed criteria.
6. Clean up and pin the head. Have one `impl` worker strip diff noise (debug output, dead code, comments that restate code, per **no-comments**), rerun the checks, and rebase into small, ordered commits. Stack follow-ups. Use the **sequence-verifiable-units** principle skill, building, verifying, and committing each small unit before the next. Leave the check table and its tests unchanged. The code is now final; pin that head.
7. Review the pinned head once. Use the [code review continuity rule](../SKILL.md#code-review-continuity) for the [structure](../../../templates/review-structure.md) and [behavior](../../../templates/review-behavior.md) reviewers. The behavior reviewer judges the head by `checks.md`. If waived, verify against the agreed criteria instead. A feature pass is not evidence that a product hypothesis is supported. "Inconclusive" or wrong-surface is not a pass. Flag it. No worker writes while review runs. For blocking findings, one worker fixes them, pin the new head, and re-review only the perspectives the change affects. Record the passing head SHA and both review run IDs.
   Keep discoveries outside the agreed scope in the worker or review report as non-blocking findings. Do not add them to the PRD, `checks.md`, or its evidence folder, or expand the implementation to fix them. If an in-scope check needs to change or an unresolved contract conflict prevents the agreed work, ask the user. The answer is a user decision: record it verbatim under `checks.md`'s 사용자 결정 section, fix the code and `checks.md` rows it affects, and continue. The PRD files stay unchanged.
8. If the design is contested, `interrogate` before shipping.
9. Run **Opening a PR** with the reviewed head, and hand the review worktree path, head SHA, latest run IDs and row evidence to Babysit and Shipping.

Code-coupled work (one feature, one migration) goes to a single owner with the checkpoint inline. That owner fans out internally after the blocking phase. Parent-level fan-out is for slices that produce independent artifacts (audits, cross-subsystem investigations, competing experiments). Rewrite the checkpoint at phase boundaries. Spawn a fresh owner rather than chaining interrupts.

**Reply:** what you built, what you chose and why, the throughput checkpoint, open decisions. Tables for design alternatives.
