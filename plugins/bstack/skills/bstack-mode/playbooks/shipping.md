### Shipping

**Claude leads the handoff, not the merge.** Fill in the [Shipping brief](../../../templates/shipping-brief.md) and launch it from the target repository with `"$BSTACK_RUN" run --role impl --brief "$SHIPPING_BRIEF" --bg`, where `BSTACK_RUN` is the absolute path supplied in the brief. Use an OpenCode-backed OpenAI model (the shipped `impl` model is `openai/gpt-6.2-sol`; explicitly select an OpenAI `--model` if the configured default differs). Wait for the worker's terminal report and check its verdict and forge evidence. Do not run reviews, retarget or merge PRs, or watch the stack yourself. The worker executes the steps below.

1. **Resolve the forge and review each PR in two independent sessions.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Pin the forge, repo and PR, target base ref and full base/head SHAs, and criteria document identity (step 4). When the handoff carries passing structure and behavior verdicts with their reviewed SHAs, start with step 3 and re-review only the perspectives whose inputs changed. Otherwise give both reviewers those inputs, criteria, and prior evidence. Launch the [structure reviewer](../../../templates/review-structure.md) and [behavior reviewer](../../../templates/review-behavior.md) in parallel, each with `"$BSTACK_RUN" run --role review --worktree --brief "$REVIEW_BRIEF" --bg` and its own brief and run ID. Wait for both and read their terminal results. Neither may have authored the change. In-session helpers such as oc-lite runner are not independent reviewers. Structure traces contract producers to consumers, retired paths, and exceptions. Behavior runs the change as a user would, via the project's verification skill or named driver, base against head, and checks that verification detects defects. Author logs, green CI, and bot approval cannot replace that independent actual-surface run.

   For a new feature, carry forward the implementation handoff's approved PRD or the user's explicit waiver; absence of a PRD is not a waiver. With a PRD, give the independent verifier the approved index, relevant F cells, and `checks.md` at the reviewed head. Use the approved `F-xx/검증` cells as PASS/FAIL criteria on their specified surfaces, with the evidence each cell requires. Carry H checks whose observation is not due as pending (owner, time, rule, evidence location), not PASS. If the PRD was waived or not required, use the agreed work criteria and keep both independent reviews.

   Parse each review result as JSON and check its perspective and pinned inputs against the brief. Each reviewer returns `PASS`, `PASS+NOTES`, or `FAIL` with evidence; a missing criterion or required evidence is `BLOCKED`, not a pass or a confirmed defect. A missing, malformed, or mismatched result does not count as a verdict. Both perspectives must pass (plain or with notes) for a PR to pass; any confirmed failure blocks landing. Send user decision items to the criteria owner and confirmed findings with their closure conditions to the implementation owner. Only the Shipping worker posts the combined verdict with reviewed base/head and evidence, and only when authorized.

2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.

3. **Reassess impact before carrying any verdict forward.** Compare the old and current base/head pairs, document (including changed criteria and history), and expected merge trees. Re-review only perspectives with changed inputs that matter to their evidence, unresolved findings, or unproven coverage. Give them the new pins, delta, and prior findings and closure conditions. Retain a passing perspective only if its evidence still applies; record original base/head SHAs, evidence and reason for reuse alongside the new pins. Identical expected merge trees can support reuse, but do not prove that changed criteria or verification environments are equivalent.

   A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` of the reviewed and current PR diffs (from each pinned pair's merge base to its head) before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. Patch-id never overrides a stale input or substitutes for fresh required checks on the current head.

4. **Guard the merge and land bottom-up, one PR at a time.** Record the PR body's `Task-Doc:` path (including absence) and the selected work document or approved PRD path and content identity when pinning step 1. Read tracked criteria from the pinned candidate head (`git show <head>:<path>`); if explicitly supplied outside the candidate, pin its digest and re-read the source. If inputs conflict or a required document cannot be read, block rather than guessing. Immediately before each merge, re-read the forge's open PR, repo, base ref, base SHA, head SHA, and document selector and identity. On GitHub use `gh pr view <pr-url> --json url,state,baseRefName,baseRefOid,headRefOid,body`; compare against the pins, not local refs. If any reviewed input changed, mark it `STALE` even with the same head. Do not issue the merge command on those verdicts. Pin the new inputs, complete step 3, and repeat this check. If a required input cannot be verified, stop as `BLOCKED`.

   For a new feature without an explicit waiver, require a PRD. When the verdict relies on a PRD, read its `approval` line (`<SHA> <run ID>`), confirm `"$BSTACK_RUN" result <run ID>` is a `READY` verdict, and confirm `git diff -M --name-status <SHA> <head> -- .bstack` shows no change to that PRD beyond adding `approval`, adding or editing `checks.md`, and an archive move (`R100`). Check it against the handed-off approval and scope. If required approval is missing or the PRD changed beyond that, stop as `BLOCKED` and report it to the lead. Criteria changes after approval live in `checks.md`'s 사용자 결정 section; verify the evidence they affect again. Existing code review and merge authority are unchanged.

   Archive the PRD before the merge that lands the last PR it needs. On that PR's branch, run `git mv .bstack/NAME .bstack/archive/NAME`, commit the move, and push within the authorized scope. Pin the new head and apply step 3; the only delta is the PRD move. If the run stops below that PR, do not archive.

   With both reviews current and required checks and repository merge conditions met, merge only the lowest unmerged PR, and only into trunk. Use `gh pr merge <pr-url> --squash --match-head-commit <reviewed-head-sha>` on GitHub. A PR built from a PRD always lands as a squash merge; on a forge or repository that cannot squash it, stop as `BLOCKED`. On Origin the plain `origin pr merge <pr>` can merge PRs below the one named; proceed only if the command targets just the lowest PR and Origin lets you verify equivalent reviewed-input conditions, including protection against landing an unreviewed head. Otherwise stop as `BLOCKED`. A fresh read is not an atomic base lock. Do not arm `--auto` or use a deferred merge that can land a different candidate; if a required queue cannot preserve the reviewed inputs through landing, block rather than enqueue.

   Read the PR back (`origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName,mergeCommit`). Command success, a confirmed queue entry, and an auto-merge request are not a merge. Report `PENDING` only for a confirmed queue entry, and `MERGED` only when the forge shows merged into trunk, with the merge commit. After a confirmed merge, retarget the next PR whose base was the merged branch to trunk (`origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease` only within the authorized stack scope. Re-pin and apply step 3 before the next merge; the expected retarget still changes the reviewed inputs.

5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only branch or base change. If the forge queued an eligible PR, the Shipping worker monitors it read-only and does not advance until the merge is confirmed. On GitHub, invoke the bstack-mode skill's `scripts/watch-pr/watch-pr` by absolute path from the target repo. Use `--queued-stack` with the run's PR numbers bottom-to-top in `--stack-prs` (same list on restart). At `ADVANCE` or `COMPLETE`, confirm the merge on the forge and continue step 4 if there is a next PR; do not wait for `COMPLETE` to process the next PR. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns. An expected move to trunk is not damage to repair. If the queue stalls or inputs drift, stop advancing, report the state, and assess the impact before any further merge attempt.

6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

7. **Clean up this pass's worktrees.** After the last merge or stop, run the bstack-mode skill's `scripts/worktree-audit.sh -b origin/<trunk> <repo>`. Remove, per the [Worktree cleanup](worktree-cleanup.md) step 5 commands, only worktrees that this pass's reviewer runs created or whose branch is a PR this pass merged, and only when they are clean and no active run uses them. Keep every other worktree and anything with uncommitted edits, and list each with its reason. Leave simulators and caches alone.

**Worker reply:** use the Shipping brief's report format. **Claude reply:** summarize what the worker confirmed landed, the verified run and ceiling, and what the next gap needs. Do not infer a merge from a successful worker run.
