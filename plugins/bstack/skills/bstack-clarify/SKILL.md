# PRD를 승인까지 만든다

목표는 **어떤 성공 기준을, 어떤 근거로 잡았고, 어떤 검증으로 그 성공을 증명하는가**를 명확히 하는 것이다. `.bstack/<name>/index.md`와 참조 문서를 완성하고 독립 승인을 받아라. 안내나 초안 제출은 완료가 아니다. 기준·근거·검증이 맞물리면 구현 방법을 미리 정하지 않아도 같은 관찰에서 같은 판정이 나온다. 제품 가설이 이미 입증됐을 필요는 없다.

명령은 `${CLAUDE_PLUGIN_ROOT}/bin/` 아래 절대경로로, 작업 레포 루트에서 실행한다. Claude는 대화·결정·위임을 맡고 조사·실험·문서 작성은 작업자에게 맡긴다. 초기 응답에 이번 작업의 성공·검증·근거를 짧게 밝히되 같은 턴에 실행으로 이어간다.

## 1. 시작하고 완료 판정부터 잡는다

사용자가 정한 이름 또는 이번 요청을 드러내는 짧은 작업명을 쓴다. 기존 PRD는 그 이름의 `.bstack/<name>/request.md`가 있고 원문이 같은 작업임을 확인한 경우에만 읽고 재개한다. `request.md`가 없는 폴더, 요청과 이름이 맞지 않는 폴더(옛 도구의 해시 이름 등), `.bstack/archive/`와 그 내용은 PRD로 읽지 않는다. 최신 폴더로 대신하지 않는다. 이름이 소문자 kebab-case가 아니거나 `runs`, `scratch`, `archive`이거나 기존 폴더가 재개 조건을 충족하지 않으면, 유효한 빈 이름으로 바꾸고 기존 폴더는 건드리지 않는다.

관련 요청과 답변의 원문 기록은 스킬 계약의 일부다. `.bstack`에 이를 보존해도 되는지 따로 묻지 않는다. 첫 요청과 이후 답변 전문을 한 줄마다 `> `를 붙여 [원문 템플릿](references/template/request.md) 형식으로 기록한다. 접두어 뒤에는 원문을 그대로 두고, 에이전트가 붙이는 소제목·질문 요지·설명은 인용 밖에 둔다. 전체 brief를 `bstack-prd start <name> --brief -`의 stdin에 넘긴다. 셸에서는 전체 brief를 리터럴로 안전하게 인용한 단일 인자로 `printf '%s'`에 주고 CLI에 파이프한다. 원문과 작업자 brief를 위한 임시 파일은 쓰지 않는다. 허용된 작업자 임시 산출물이 필요하면 레포 외부의 `$BSTACK_WORK_DIR`를 사용한다.

도구가 반환한 PRD 폴더에서 이어간다. 같은 작업의 기존 PRD라면 `bstack-prd status <name>`을 확인한다. 새 답이나 범위 변경이 없고 현재본이 `approved`면 그 index와 run ID를 인계한다. 새 답이나 범위 변경이 있으면 기존 `request.md`의 바이트를 보존하고 위 방식으로 답 원문을 붙인 전체 brief를 `start --brief -`에 다시 넘긴다. 새 답은 과거 승인을 무효로 만든다. 새 답 없이 재개한 미승인본의 `revise_count`가 2 이상이면 후보를 고치기 전에 재작업 한도 대응으로 간다.

[PRD 작성 기준](references/prd-format.md)의 `성공 정의 / 검증 / 근거`를 제품 가설(H)과 기능(F)에 대입한다. 사용자 원문에서 분명한 것은 고정한다. **어떤 답이나 관찰이 범위·의도·합격선을 바꿀 때만** 그 공백을 좁힌다. 목표 불확실성은 여기서 해소하고, 어느 구현으로도 같은 판정 기준을 충족할 수 있다면 그 선택은 넘긴다.

## 2. 판단이 갈리는 곳만 좁힌다

**결과가 사용자가 보는 장면을 바꾸면 질문하고, 같은 장면을 어떻게 만들거나 관찰할지의 문제면 실험한다.** 새 게임·제품 규칙이 필요하면 실험으로 규칙을 굳히기 전에 “어떤 장면이어야 하나요?”라고 묻는다. 예를 들어 낙하 중 새 판이 겹친다면 보충 시점을 미루거나 마지막 판을 정하는 대신, 새 판이 어디에 나타나고 플레이어가 있는 칸은 어떻게 보여야 하는지 먼저 묻는다. 이미 정해진 장면의 실현 가능성과 관찰 수단은 답을 기다리는 동안에도 독립적으로 확인할 수 있다.

- 레포·문서·이력에 답이 있다면 `explore`에게 출처와 관찰을 맡긴다.
- 돌려 봐야 안다면 `impl`에게 제품 코드를 고치지 않는 격리 실험을 맡긴다. H와 F 모두 **검증 환경 접근 및 관찰 수단이 실제로 되는 근거**를 확보한다. 기존 예행 기록을 재사용할 수 있고, 아직 없는 기능의 성공을 증명할 필요는 없다.
- 가치·범위·권한처럼 사용자가 정해야 할 것은 Claude가 `AskUserQuestion`으로 묻는다. 대안과 **답이 바꿀 셀**을 붙인다. 도구를 쓸 수 없으면 남은 독립 작업을 진행한 뒤 질문과 셀을 메시지로 남기고 그 턴을 미완료로 끝낸다. 답을 받으면 1절의 방식으로 보존하고 해당 셀부터 이어간다.
- 기본 수단으로 안 풀리는 용어·측정·판정 경계에는 [메서드 표](references/methods.md)에서 해당 원본만 연다.

작업자 brief에 필요한 셀, 어떤 관찰이 선택을 바꾸는지, 읽을 절대경로와 쓰기 범위를 넣어 `bstack-run run --role explore|impl --brief -`의 stdin으로 보낸다(`|`는 역할 택일). 오래 걸리는 독립 작업은 병렬로 맡길 수 있다. 비동기면 `wait` 후, 모든 run은 `bstack-run status <id>`의 `status`가 `done`이고 `exit_code`가 `0`인지 확인한 뒤에만 `result`의 요약(셀, 관찰, 출처, 남은 결정)을 읽는다. 조건 미달이나 빈 결과는 작업 실패로 다룬다. 논의 중에는 원문만 추가하고 PRD 본문을 매번 쓰지 않는다.

## 3. 후보를 한 번에 쓴다

판단을 바꿀 공백이 닫히면 `impl` 한 명에게 반환된 폴더, 원문, 출처가 붙은 결정, 조사·실험 결과, [작성 기준](references/prd-format.md)을 준다. [예시](references/example-prd/index.md)는 모양이 필요할 때 본다. 작성자는 표와 필요한 상세만 한 묶음으로 쓰고, 정해지지 않은 범위나 합격선을 발명하지 않는다. 모르는 결정은 Claude에게 돌려준다. Claude나 작업자는 승인 상태를 파일이나 frontmatter에 쓰지 않는다.

## 4. 후보를 사용자에게 확인받는다

후보를 쓴 뒤 검수 전에 **사용자가 정한 기준(원문 첨부)**, **에이전트가 정한 기준(제안 이유와 어떤 계약·검증에 필요한지)** 순서로 묶어 보여 준다. 양쪽 모두 행별 성공 기준, 검증 요약, 근거 ①과 검증이 보장하는 범위·한계인 근거 ②를 제시한다. 위의 질문 방식으로 “이렇게 할까요? 두 번째 묶음은 제안입니다. 필수로 삼거나 뺄 항목이 있나요?”라고 한 번에 묻는다. 일반적 진행 동의는 후보 제출 확인이지 제안 전체의 채택이 아니다. 특정 기준의 명시 채택·변경만 답 원문과 채택 대상에 연결한다.

사용자 확인을 받을 때까지 검수하지 않는다. 답은 1절의 방식으로 보존하고, 변경 요청이면 영향받는 내용을 고쳐 다시 확인받는다. 재작업에서 이미 확인받은 기준·근거·검증의 내용이 바뀌어도 다시 확인받는다.

이번 요청에서 사용자가 명시적으로 자율 진행을 허락한 경우에만(예: “알아서 끝까지”, “확인 없이 진행”) 이 확인을 건너뛴다. Claude가 이번 요청의 원문에서 판단하고, 건너뛸 때 근거가 된 사용자 문장을 `request.md`에 그대로 인용해 남긴다. 도구는 이를 강제하지 않는다. 자율 진행 허락은 필요한 사용자 결정, 재작업 한도, 독립 검수를 면제하지 않는다.

## 5. 검수하고, 다음 행동으로 잇는다

확인을 받았거나 명시적인 자율 진행이 허용됐으면 `bstack-prd review <name>`을 실행한다. 도구는 빈 인덱스나 그대로인 템플릿, 없는 원문 파일, H/F 행 누락만 사전 검사한다. 작성 형식·참조·근거는 원문과 전체 후보를 받은 [독립 검수자](references/reviewer.md)가 판단한다.

| 결과 | 다음 행동 |
|---|---|
| `READY` | `status <name>`이 현재본에 `approved`라고 하는지 확인한다. 아니면 원문·후보 변경을 확인하고 다시 제출한다. |
| `REVISE` | `status <name>`의 `revise_count`가 2 이상이면 아래 재작업 한도 대응으로 간다. 그 전에는 해소 조건을 작성자에게 보내 한 묶음으로 수정한다. 새 증거가 필요하면 먼저 조사·실험한다. 바뀐 셀과 영향받는 참조를 확인하고, 필요한 사용자 확인을 거쳐 재검수한다. 문구만 고치지 말고 지적된 전제·증거·결정을 다시 확인한다. 근거를 덧붙이지 말고 해당 셀을 고쳐 쓰며, 해소되어 더는 판단에 쓰지 않는 근거와 상세는 지운다. |
| `rework_limit_reached` (종료 4) | 검수자는 실행되지 않았다. 아래 재작업 한도 대응으로 간다. |
| `BLOCKED` | 지적에 필요한 사용자 결정을 위의 질문 방식으로 묻는다. 답을 보존한 뒤 영향받는 셀을 작성하고 사용자 확인을 거쳐 재검수한다. |
| 실행 오류 (`preflight_failed`, `review_in_progress`, `review_run_failed`, `invalid_verdict`, `submission_changed` 등) | 유효 판정이 아니다. 출력 사유를 보고 원인을 해결한 뒤 현재본으로 새 검수를 실행한다. 반영되지 않은 판정은 버리고 추정하거나 직접 고치지 않는다. 복구할 수 없으면 미완료로 남긴다. |

**재작업 한도:** 같은 `request.md`로 두 번 `REVISE`를 받으면 더 고치거나 검수하지 않는다. `revise_records`의 두 지적을 요약하고, 무엇이 왜 통과하지 못했는지와 어떤 선택지가 어느 셀을 바꾸는지 보여 주고 사용자와 쟁점을 다듬는다. 실제 답을 받아 위의 `start` 방식으로 `request.md`에 추가한 뒤 영향받는 셀부터 이어 간다. 원문 해시가 달라지면 횟수는 0부터 센다.

원인이 해결되지 않는 도구·작업자 장애, 사용자 답 대기, 명시적 중단은 정당한 **미완료**다. 같은 실패를 맹목적으로 반복하지 말고 경로, 막힌 셀 또는 실패 이유, 재개에 필요한 답·조치를 남긴다. 작업이 더 가능한데 단답·진행 예고로 턴을 끝내지는 않는다.

현재본이 승인되면 index 경로와 행별 요점, 독립 run ID와 승인 이유, 남은 가정과 제품 가설의 관찰 시점을 보고한다. 원래 플레이북에는 승인본을 인계하되 구현·병합 권한을 새로 얻은 것으로 보지 않는다.
