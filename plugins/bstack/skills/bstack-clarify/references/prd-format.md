# PRD: 성공 기준·근거·검증의 인덱스

각 행은 어떤 성공 기준을, 어떤 근거로 잡았고, 어떤 검증으로 그 성공을 증명하는지 연결한다. 같은 관찰에서 같은 판정이 나오는 것은 이 연결의 결과다.

`.bstack/<name>/`에 `index.md`, `request.md`, 필요한 상세 Markdown만 둔다. PRD가 근거로 링크하는 실험 결과나 로그는 `evidence/`에 두고 링크한다. `index.md`에서 링크로 닿지 않는 파일은 남기지 않는다. 링크하지 않는 실험 기록은 작업자의 `BSTACK_WORK_DIR`에 둔다. `start`는 [인덱스 템플릿](template/index.md)으로 초기화한다. 요청 원문 보존은 [clarify의 시작·재개 절](../SKILL.md)을 따른다. `reviews/`는 도구 전용이다.

`index.md`에는 목표, 포함·제외 범위, 판정표, 가정과 미결정을 적는다. 제외에는 사용자 답이나 기존에 적용되는 계약 등 **결정 출처**를 단다. 원문보다 적용 대상을 좁히는 정책은 가정으로 몰래 넘기지 않는다. 범위에는 **영향받는 기존 계약**도 적는다. 이번 변경이 닿는 기존 계약을 찾고, 계약마다 유지·변경·제외 중 어떻게 할지와 그 출처를 한 줄로 쓴다. 어떻게 할지 판단이 서지 않으면 사용자에게 묻는다. 유지하는 계약의 회귀 검증은 구현 검수에서 다룬다. 미결정은 `A-xx`로 가리키고 합격선을 바꾸지 않는 이유를 쓴다. 가정이 깨졌을 때 별도로 판정할 필요가 있으면 검증 규칙에 적는다.

| ID | 성공 정의 | 검증 | 근거 |
|---|---|---|---|
| H-01 | 제품 가설: 대상, 달라질 결과, 기준선과 목표(해당하면). 기능 배포 자체와 구별. | 관찰자, 환경·대상·기간·출처, 시나리오, 지지/기각/판정불가 규칙, 증거 및 기록 위치. | ① 에이전트: 왜 이 결과와 기준을 제안하는가 ② 어느 집단과 조건에서 무엇을 말할 수 있는가(교란과 한계 포함). |
| F-01 (→H-01) | 기능: 전제 → 행동 → 관찰 결과, 보존 또는 금지할 결과. | 환경, 시나리오, 관찰, pass/fail, 증거 형태. 내부 구현 대신 실제 판정 표면을 지정. | ① 사용자 「원문 발췌」와 필요시 결정 문맥 ② 관찰이 어떤 깨진 동작을 가르며 어느 상태까지 보장하는가. |

ID는 고정하고 지운 ID는 재사용하지 않는다. 기능마다 기여하는 H를 적는다. 셀은 `F-01/검증`으로 가리킨다. 짧게 요약하고 필요할 때 `상세.md#앵커`로 이어 간다. 자료구조, 계산 방법, 갱신 주기 같은 구현 예시는 쓰지 않는다. 관찰 수단이 실제로 된다는 근거까지만 적는다.

근거 ①은 `사용자 「원문 발췌」` 또는 `에이전트: 이유`로 시작한다(H/F 모두 어느 쪽이든 가능하다). 사용자 기준은 `request.md`의 인용 블록에서 원문을 그대로 발췌한다. 링크나 줄 번호는 덧붙일 수 있지만 원문 인용을 대신하지 않는다. 특정 기준을 명시 채택한 경우 답 원문과 함께 무엇을 채택했는지 적는다. 포괄 동의를 단독 인용하거나 이를 근거로 제안 전체를 사용자 결정으로 바꾸지 않는다.

한 행에는 같은 출처의 성공 기준을 넣는다. 검증 셀의 관찰법은 기본적으로 제안이므로 방법이 다르다는 이유로 행을 나누지 않는다. 변경하는 계약의 새 결과는 판정표의 행으로 쓴다. 바뀔 수 있는 외부 자료가 판정의 근거라면 필요한 발췌와 버전·출처를 후보 안에 둔다.

검증은 두 층이다. **지금은 판정 기준을 고정한다.** H/F 모두 환경에 접근하고 데이터를 읽거나 결과를 관찰할 수 있다는 근거(예행 run, 하네스, 접근 확인 등)를 붙인다. 예행은 아직 없는 동작이 통과했다는 뜻이 아니다. **명령 + EXPECT는 구현 계획·구현에서 만든다.** 기준을 약화할 수 없으며, 이미 있는 명령은 PRD에 적어도 된다. 승인된 기준을 바꾸면 현 내용은 재승인이 필요하다.

독립 검수는 [공통 검수 머리말](../../../templates/preamble/reviewer.md)을 먼저 적용하고 [PRD 검수 지시](reviewer.md)를 따른다.
