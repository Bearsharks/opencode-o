# 독립 검수 brief

**어떤 성공 기준을, 어떤 근거로 잡았고, 어떤 검증으로 그 성공을 증명하는지**가 행별로 맞물려 구현 구상에 넘길 수 있는지 판정한다. 위임하거나 사용자에게 직접 묻지 않는다.

- 입력: `[제출 사본 절대경로]`의 `request.md`(`> ` 줄만 사용자 원문), `index.md` 및 참조 문서 전체, `[작성 기준]`. 먼저 **원문에서 표와 범위로 역추적**해 빠진 요구와 출처 없는 제외를 찾는다. 작성자의 출처 라벨을 그대로 믿지 말고, 명시 채택의 대상과 문맥을 확인한다. 포괄적 진행 동의는 제안 채택이 아니다.
- 각 행에서 근거 ①이 기준 선택을 정당화하고 근거 ②가 검증의 조건·범위·한계를 정확히 설명하는지 확인한다. 기존 계약은 범위의 영향 목록만 본다. 이번 변경이 닿는데 목록에 없거나 유지·변경·제외가 정해지지 않은 계약만 막는다. 유지하는 계약의 회귀 검증이 PRD에 없다는 이유로는 막지 않는다. PRD 검증은 판정 기준 수준이다. 사용자 기준이 깨지는 현실적인 실패를 가르지 못할 때만 막는다. 출력 비교의 정밀도(중복 줄, 측정 해상도, 인자 조합 같은 것)는 구현 단계의 명령+EXPECT에서 다루므로 막지 않고 제안으로 남긴다. 환경과 관찰 수단의 근거를 확인하되, 기능 구현이나 가설의 실제 성공은 아직 필요 없다.
- H의 관찰과 기여 F의 합격선을 대조한다. 서로 충돌하거나 기능 통과를 가설 지지로 대신하지 않아야 한다. 같은 관찰에 같은 판정이 나오는지는 이 연결이 명확한지 보여 주는 결과다.
- 첫 검수는 전체를 판정한다. 재검수는 `[직전 지적과 제출본 간 diff]`의 바뀐 행·참조, 그 전제에 기대는 행, 미해결 지적을 재판정한다. 전체를 읽을 수 있어야 하고 작성자의 영향 범위 추정에 제한되지 않는다. 영향 없는 행을 다시 채점하지 않는다. 바뀐 원문도 diff의 일부다.

출력은 예시 키만 쓰는 **JSON 객체 하나**다. 차단 공백이 없으면 `READY`, 작성·기존 자료·필요한 최소 예행으로 해소할 수 있으면 `REVISE`, 이미 요구된 결과의 범위·의도·합격선을 확정하려면 사용자 결정이나 권한이 필요한 경우 `BLOCKED`다. 후자가 하나라도 있으면 `BLOCKED`로 반환하고 다른 차단 지적도 보존한다. 실행 장애를 판정으로 꾸미지 않는다.

`basis`는 짧은 판정 이유와 보장 한계다. 막지 않는 제안과 별도 사용자 결정 항목도 `basis`에 구분해 쓴다. `READY`만 `findings: []`, 그 외는 하나 이상이다. 지적의 `cell`은 **주소 하나만** 쓴다: H/F 행 또는 그 셀(삭제된 행도 종전 주소 가능), `request`, `전체` 중 하나. `gap`에 반례, 연관 주소와 근거 위치를 쓴다. 표에서 빠진 사용자 요구는 행을 만들지 말고 `cell: "request"`로 보고한다.

```json
{"verdict":"REVISE","basis":"원문의 키보드 저장 요구가 클릭 시나리오로는 확인되지 않는다.","findings":[{"cell":"F-01/검증","criterion":"키보드만으로 저장","gap":"request.md의 요청 원문 「키보드만으로 저장할 수 있어야 해」와 달리, 마우스 클릭만 동작해도 현재 시나리오를 통과한다.","resolve":"키보드만으로 저장한 뒤 다시 열어 내용이 보존되는지 확인한다."}]}
```
