# Setup bstack

1. See the current defaults with `bstack-run config` (`"${CLAUDE_PLUGIN_ROOT}/bin/bstack-run" config`, or use the absolute plugin path). Read the reported config file, honoring `BSTACK_CONFIG` if set. Run `oc-lite models` to discover OpenCode IDs. If discovery fails, report it and leave the file untouched; do not guess.
2. Use `AskUserQuestion` to confirm each role and ordered panel seat. Offer only OpenCode IDs listed by `oc-lite models`. Use `provider/model` for the model default and `provider/model#variant` for an explicit supported variant; if variants are not listed, use the default unless the user confirms support. Claude seats are not listed by `oc-lite models`: preserve them unless the user changes them, and accept only `claude:haiku`, `claude:sonnet`, and `claude:opus`, never `claude:fable`. Verify both bare `provider/model` IDs in each `fast` mapping against `oc-lite models`; do not infer mappings from suffixes, and leave `zai-coding-plan/glm-5.4` unmapped.
3. Show the proposed changes and get approval before writing. Send only the changed top-level keys among `roles`, `fast`, and `deny`, each with its full approved value. `impl`, `hard`, `explore`, and `review` are strings (`review` is the model for every independent review); `panel` is an ordered, nonempty array of strings. Keep the current `deny` unless the user approves a change. Reject models containing a denied substring in the resulting `deny`, case-insensitively, including variants. If a choice is unavailable or the user cancels, do not write.
4. Pipe the approved JSON object to `python3 "${CLAUDE_PLUGIN_ROOT}/skills/setup-bstack/write-models.py"` (use the same plugin path, working directory, and `BSTACK_CONFIG` as in step 1). The helper runs `bstack-run config` before writing, validates the staged merge, atomically replaces the file while preserving permissions, and runs `bstack-run config` again on the installed file. It compares the parsed JSON before and after to verify that every key outside the approved update, including `cli`, `preamble`, and `claude`, remains unchanged. Report the updated path and the resulting settings only if the helper succeeds. If the config is not writable, ask for a writable copy; do not create a shadow config.

See the [Claude Code harness](../../docs/harness/claude-code.md) for the launcher path and completion handling. Changes are used on the next launch, not on work already running. Use `/bstack:create-verification-skill` separately when the project needs a live verification harness.
