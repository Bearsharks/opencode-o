# 기능 PRD

`.bstack/<name>/index.md`를 아래 형태로 완성해 독립 승인을 받는다. **형태는 지킨다.** 무엇을 조사하고 묻고 실험할지는 상황에 맞게 정한다. 기획만 하고, 어떻게 만들지는 구현 단계에 둔다.

명령은 `${CLAUDE_PLUGIN_ROOT}/bin/` 아래 절대경로로, 작업 레포 루트에서 실행한다. Claude는 대화와 결정을 맡고, 조사·실험·문서 작성은 `bstack-run`으로 작업자에게 맡긴다.

## PRD 형태

[템플릿](references/template/index.md)을 따른다.

- **목표:** 무엇을 이루려는가. 같은 폴더에 확인된 `hypothesis.md`가 있으면 링크한다. 없으면 누가 어떤 문제를 겪는지와 그 증거를 2~3줄로 쓴다. 증거가 없으면 `미정: <확인 방법>`으로 남긴다.
- **범위:** 포함할 기능, 만들지 않는 것과 그 이유·출처.
- **요구사항:** 기능 하나에 한 행이다. 한 기능의 요구가 여럿이면 성공 정의에 항목으로 적는다.
  - **성공 정의:** 사용자에게 보여야 할 결과.
  - **성공 정의 근거:** 왜 그것이 성공인가. 사용자 기준은 `사용자 「원문 발췌」`로 시작하고, `request.md`의 인용에서 그대로 옮긴다.
  - **검증:** 어디서 무엇을 보고 통과로 판정하는가. 명령과 EXPECT는 구현 단계에서 만든다.
  - **검증 근거:** 왜 그 관찰이 성공을 보여 주는가. 관찰 수단이 실제로 있다는 근거(기존 테스트, 예행, 접근 확인)를 붙인다.
  - 가설이 있으면 ID 옆에 기여하는 가설을 `F-01 (→H-01)`로 적는다. 기여하지 않지만 사용자가 원한 기능은 `(H 없음)`으로 적는다.
- **정책:** 이번 변경이 닿는 기존 정책마다 현재 동작과 출처, 유지 또는 수정, 결정 출처를 쓴다. 수정하는 정책의 새 동작은 요구사항 행에 쓴다. 판단이 서지 않으면 사용자에게 묻는다.
- **에이전트 제안:** 사용자가 정하지 않은 기준과 그 이유. 채택 전에는 판정에 쓰지 않는다. 채택되면 요구사항 행으로 옮기고 채택한 답의 원문을 근거로 단다.
- **열린 질문:** 범위나 기준을 바꿀 수 있는 미결정 항목.

파일, 자료구조, 라이브러리, 작업 분해 같은 구현 설계는 쓰지 않는다. 모르는 것을 그럴듯하게 지어내지 않는다. 작업자는 최종 결과로 보고한다. 버릴 실험 파일은 직접 만든 임시 디렉터리(예: `mktemp -d`)에 두고 작업이 끝나기 전에 디렉터리를 삭제한다. PRD가 링크하는 증거는 `.bstack/<name>/evidence/`에 둔다. 다른 임시 작업 공간은 쓰지 않는다.

## 진행

- **원문 기록:** 첫 요청과 이후 답변 전문을 한 줄마다 `> `를 붙여 [원문 템플릿](references/template/request.md) 형식으로 `bstack-prd start <name> --brief -`의 stdin에 넘긴다. 새 답이 오면 기존 바이트를 보존하고 덧붙인 전체를 다시 넘긴다. 기존 폴더는 같은 작업의 `request.md`가 있을 때만 이어 쓴다.
- **확인:** 문서를 쓴 뒤 검수 전에 사용자 기준(원문 첨부)과 에이전트 제안을 나눠 보이고 "이렇게 할까요? 제안 중 채택하거나 뺄 것이 있나요?"라고 묻는다. 확인을 받기 전에는 검수하지 않는다. 일반적인 진행 동의는 제안의 채택이 아니다. 사용자가 이번 요청에서 자율 진행을 명시적으로 허락했으면 확인을 건너뛰고, 그 문장을 `request.md`에 인용해 둔다.
- **검수:** `bstack-prd review <name>`을 실행한다. 검수자는 [검수 brief](references/reviewer.md)를 따른다.

| 결과 | 다음 행동 |
|---|---|
| `READY` | `bstack-prd status <name>`이 `approved`인지 확인한다. |
| `REVISE` | 지적된 셀을 고쳐 쓴다. 근거를 덧붙이지 말고, 더는 쓰지 않는 근거는 지운다. 확인받은 기준이 바뀌었으면 다시 확인받고 재검수한다. |
| `REVISE` 두 번 또는 `rework_limit_reached` | 더 고치지 않는다. 두 지적과 선택지를 사용자에게 보이고 답을 받아 원문에 추가한다. 원문이 바뀌면 횟수는 0부터 센다. |
| `BLOCKED` | 필요한 결정을 사용자에게 묻는다. |
| 실행 오류 | 유효한 판정이 아니다. 원인을 고치고 현재본으로 다시 검수한다. |

승인되면 도구가 검수 이력을 승인 기록만 남기고 정리한다.
승인되면 `index.md` 경로와 검수 run ID를 원래 플레이북에 넘긴다. 승인이 구현이나 병합 권한을 새로 주지는 않는다.
