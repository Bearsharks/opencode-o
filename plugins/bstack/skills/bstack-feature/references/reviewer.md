# PRD 검수 brief

PRD가 [기능 PRD 형태](../SKILL.md#prd-형태)를 갖추었는지 판정한다. 위임하거나 사용자에게 직접 묻지 않는다.

입력은 brief 끝에 적힌 커밋 SHA 시점의 PRD 폴더(`request.md`, `index.md`)와 참조 문서 전체다. 파일은 `git show <SHA>:<경로>`로 읽는다. 읽기만 한다. `request.md`에서는 `> ` 줄만 사용자 원문이다. `hypothesis.md`가 있으면 맥락으로만 읽고 채점하지 않는다. 작성자의 출처 표시를 그대로 믿지 말고 원문과 대조한다.

다음 중 하나에 해당할 때만 막는다.

1. 사용자 원문의 요구가 빠졌거나, 출처 없이 제외됐다.
2. 요구사항 행에 빈 칸이 있거나, 근거가 그 칸을 설명하지 못한다.
3. 기준이 원문과 다르거나, 채택되지 않은 에이전트 제안이 사용자 기준으로 적혔다.
4. 이번 변경이 닿는 기존 정책이 정책 절에 없거나, 유지·수정이 정해지지 않았다.
5. 구현 설계(파일, 자료구조, 라이브러리, 작업 분해)를 정한다.

그 밖의 의견은 막지 않는 제안이다. 기능 구현이나 가설의 실제 성공은 아직 필요 없다.

brief에 직전 검수와 diff가 있으면 재검수다. diff에서 바뀐 행과 참조, 미해결 지적만 판정한다. 바뀐 원문도 diff의 일부다.

출력은 예시 키만 쓰는 **JSON 객체 하나**다.
- `READY`: 막을 것이 없다. `findings: []`.
- `REVISE`: 작성으로 해소할 수 있다.
- `BLOCKED`: 범위·의도·합격선을 정하려면 사용자 결정이 필요하다. 이런 지적이 하나라도 있으면 `BLOCKED`로 반환하고 다른 지적도 함께 남긴다.

실행 장애를 판정으로 꾸미지 않는다. `basis`에는 짧은 판정 이유와 막지 않는 제안을 구분해 쓴다. 지적의 `cell`은 주소 하나다. `F-01`, `F-01/검증 근거` 같은 행이나 셀, `request`, `전체` 중 하나를 쓴다. `gap`에는 무엇이 빠졌거나 어긋났는지와 근거 위치를 쓴다.

```json
{"verdict":"REVISE","basis":"원문의 키보드 저장 요구가 요구사항에 없다.","findings":[{"cell":"request","criterion":"키보드만으로 저장","gap":"request.md의 「키보드만으로 저장할 수 있어야 해」가 어느 요구사항 행에도 없다.","resolve":"해당 기능 행의 성공 정의에 이 항목과 원문 근거를 넣는다."}]}
```
