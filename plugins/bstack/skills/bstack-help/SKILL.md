# Bstack help

Answer the user's question about bstack, hand them a prompt they can send, and link the file the answer came from. For a help question, don't start the work. The user asked how, and a bstack run spends real tokens, so let them send the prompt.

A message that asks for work, such as "use bstack to fix this bug", is not a help question. Read [`bstack-mode`](../bstack-mode/SKILL.md), do the work under it,.

This file maps questions to the skills and guide pages that hold the answers. Those files own the details. Read the file you route to before you quote it, and trust it when it disagrees with this map. Link to the installed bstack file rather than sending the user to an upstream version.

## Find out what they need

Infer the need from the message and the conversation. A named situation, such as "which skill reviews a PR?", goes straight to its section. If the need is still unclear, ask one multiple-choice question with these options, then answer only the section they pick:

- Get set up
- Start a task with `/bstack-mode`
- Pick a skill for a situation
- Fix a run that went wrong
- Make bstack my own

Check the state that changes the answer, and mention it only when it does:

- No `verify-*` skill or other app harness in the project means agents have no scripted way to drive the app. Mention `/create-verification-skill` when the question is about proving a change works.
- No formal verification skill in the project means no property is checked past what tests reach. Mention `/create-formal-verification-skill` when the question is about a race, an invariant, or another case tests rarely hit. When one exists and the code it covers changed after the commit it records as last in sync, mention `/maintain-formal-verification-skill` if the question touches that code.

## Get set up

1. Start Claude Code with `claude --plugin-dir /absolute/path/to/plugins/bstack` from the target project.
2. Run [`/bstack:setup-bstack`](../setup-bstack/SKILL.md) to choose available worker models and optional variants. It writes `config/models.json`; each new worker launch uses the current file. To reduce costs, choose a cheaper model or supported variant, or shorten a panel when the workflow still has enough independent seats.
3. Start with `/bstack:bstack-mode`, a goal, and a check that can pass or fail.

The [README](../../README.md), [guide page 1](../../docs/guide/01-setup.md), and [Claude Code harness](../../docs/harness/claude-code.md) have details. Use the `bstack:` prefix when invoking plugin skills; the examples below sometimes shorten it.

## Start a task with `/bstack-mode`

`/bstack-mode` matches the task to a playbook, copies the playbook's steps into the todo list, and runs the other skills as the steps need them. A good prompt states the goal and how to tell it's done. It doesn't list skills, because a hand-written sequence tends to drop or reorder steps the playbook would keep. Read [`references/prompting.md`](references/prompting.md) before you help word one. [Guide page 2](../../docs/guide/02-bstack-mode.md) has examples.

Start a new task with `/bstack:bstack-mode` again. Mid-chat, saying "new task" tells the coordinator to match a fresh playbook.

If a skill directory next to this one is missing from the table, read its frontmatter and route by its description. The `principle-*` directories are covered under principles below.

Close calls:

- `/how` explains what the code does. `/why` explains the reasons. `/teach` runs one or both and explains the result plainly.
- `/arena` gives every worker the same brief and merges the best parts. `/swarm` splits work into slices or a race and returns one report.
- `/interrogate` reviews the diff. `/blast-radius` looks for breakage outside the diff and proves the one fact that makes the change safe.
- `/recall` rebuilds context across recent chats. `/ketchup` covers only this chat since the user's last message. Resuming one specific chat or branch is the Session pickup playbook.
- `/figure-it-out` designs one rigorous run. The Autonomous run playbook drives one task to a finish condition.

## Playbooks and principles

Playbooks are step lists inside `/bstack-mode`, not skills, so they have no slash command. Inside `/bstack-mode`, describing the task picks one, and these phrases name one directly:

- "babysit this pr" or "check on pr 123" runs Babysit. It drives the PR to merge-ready and stops there. It doesn't merge unless the user asks to merge, land, or ship.
- "land the stack" runs Shipping.
- "take over this branch" runs Session pickup.
- "pause safely" runs Pause safely.
- "full autopilot on this queue" runs Autopilot-full. "autopilot, don't merge" runs Autopilot-stack.
- "run the eval playbook" runs Eval.

The Playbooks section of [`bstack-mode`](../bstack-mode/SKILL.md) lists each playbook. [Guide page 6](../../docs/guide/06-verify-and-ship.md) covers opening, babysitting, and landing a PR.

For a written plan across phases or stacked PRs, use the [Multi-phase plan playbook](../bstack-mode/playbooks/multi-phase-plan.md), which does not implement it. For a design question, use Prototype or `/architect` first.

Principles are one-rule skills that `/bstack-mode` reads and cites in its replies. The user rarely invokes one. They steer with the names instead, as in "apply prove it works. show me the real output." Typing `/principle-<name>` still loads one on demand. [Guide page 8](../../docs/guide/08-principles.md) lists them.

## Fix a run that went wrong

| Symptom | Fix |
|---|---|
| The mode stopped applying after a few turns | Start each new task with `/bstack:bstack-mode`. |
| A question got treated as the next step of the last task | Say "new task", or say the turn doesn't need the mode. |
| A new model choice had no effect | Check the launcher and `config/models.json` belong to the same plugin copy. Changes affect future runs. |
| Runs cost more than expected | See the cost paragraph under Get set up. |
| A skill didn't load on its own | Invoke the plugin skill with its `bstack:` prefix. |
| Parallel agents overwrote each other | Give each agent its own worktree, or run them in isolated worktrees, which each get their own machine. |
| An overnight run moved but finished nothing | `/loop` needs a check that can pass or fail, not a duration. See [guide page 7](../../docs/guide/07-overnight.md). |
| The reply claims success from a green build | Ask for the real command, flow, stored value, or profile. That's the prove-it-works principle. |

For a run that drifts, [`references/prompting.md`](references/prompting.md) has one-line steers. [Guide page 10](../../docs/guide/10-recipes-and-pitfalls.md) has more pitfalls and the recipes worth copying.

## Make bstack my own

- [`/reflect`](../reflect/SKILL.md) after a session turns its lessons into skill edits the user approves.
- `/bstack-mode write a skill for <workflow>` runs the authoring playbook. The eval playbook tests a skill change blind.
- Fix a misbehaving skill in its own PR, not inside the feature work where it went wrong.

[Guide page 9](../../docs/guide/09-make-it-yours.md) covers each of these.

## Reply

Lead with the answer. Give at most one example prompt in a code block, adapted from [`references/recipes.md`](references/recipes.md) when one fits, then the link to that file. Keep it short unless the user asked for the whole map.
