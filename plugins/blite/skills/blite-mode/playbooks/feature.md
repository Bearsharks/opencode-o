### Feature

**You own the result.** The user confirms what to build, the architecture, and how each requirement is verified. Workers write the code; independent reviewers judge it against checks pinned before the code existed.

1. **PRD.** Read [the PRD skill](../../blite-feature/SKILL.md) and continue or start the PRD for this request. Do not start step 2 without an approved PRD: its `approval` line and review run ID.
2. **Architecture review.** Read [the architecture skill](../../blite-architecture/SKILL.md) and review the architecture for the approved PRD with the user. Save the confirmed version as `.bstack/<name>/design.md`. Do not start step 3 before that.
3. **Verification review and pinning.** For each PRD requirement, write a row in `.bstack/<name>/checks.md` from the [check table template](../../blite-feature/references/template/checks.md): its 성공 정의 as the purpose, and what will be run and what counts as passing. Review the table with the user. After they confirm it, an `impl` worker prepares the tests it names without changing production code and adds their paths and names to the table. Before the table is pinned, the worker runs every row's method on the code as it is. Where the purpose is not yet met, the method fails because the behavior is missing, not because of setup. A test that was written but not run does not count. Results of running them go in the worker report, not the table. Read those results with the table; a row whose result does not match goes back to the worker, or to the user if the method itself must change. Then commit the table with its tests and record that commit as the check SHA.
4. **Implement.** Give an `impl` worker `design.md`, the approved `index.md` with its 정책 section, the check SHA, and `checks.md`. The table and its tests stay as pinned: `git diff <check SHA> HEAD -- <test paths>` stays empty, and `checks.md` stays identical to its copy at the check SHA wherever the PRD folder sits. A worker that finds a check or the design wrong stops and reports.
5. **Clean up and open the PR.** An `impl` worker strips diff noise (debug output, dead code, comments that restate the code), reruns the checks, and leaves small ordered commits. Move the PRD with `git mv .bstack/<name> .bstack/archive/<name>` and commit. Push the branch and open a ready PR from this head: title `type(scope): subject`, body under 40 lines with `## Why`, `## What changed`, `## Verification`. Pin that head. The code is now final.
6. **Review and merge.** Run [Shipping](shipping.md). On `FAIL`, one `impl` worker finds why the findings were missed and fixes the change; on `STALE`, one rebases onto the current base. Either way it reruns the checks, and you send the new head to the same Shipping run with `bstack-run ask`. Stop at `MERGED` or at a blocker the user must decide. Rework at most twice; before a third, wait for the user's approval.

Work that is not in `checks.md` and needs doing later goes in the backlog, whether a reviewer or a worker found it. Do not add it to the PRD or `checks.md`, or expand the work to fix it. After `MERGED`, update the base branch, add these items to `.bstack/backlog.md` (start it from the [backlog template](../../blite-feature/references/template/backlog.md)), commit, and push. If the confirmed design or an in-scope check must change, or a contract conflict blocks the agreed work, ask the user. Append the answer verbatim to `request.md`, update the PRD, `design.md`, and `checks.md` where it affects them, fix the code, pin a new check SHA, and continue. A user decision needs no new PRD review.

**Reply:** what was built, each requirement with the evidence that passed it, the merge commit, and open decisions.
