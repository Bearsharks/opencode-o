### Feature

**You own the result.** The user approves the PRD, the architecture, and how each requirement is verified, each before its artifact is written. Workers write the code; independent reviewers judge it against checks pinned before the code existed.

Steps 1 to 3 run the same way. Propose to the user and explain why, showing each decision with its options and their effects. Write the artifact only from the version they approved, and do not start the next step before it exists. Approval holds for the version shown; if it changes later, show the change and ask again. An answer that settles some decisions while raising new questions or alternatives is not approval.

1. **PRD.** Read [the PRD skill](../../blite-feature/SKILL.md) and follow it for this request. The artifact is `index.md` with its `approval` line and review run ID.
2. **Architecture.** Read [the architecture skill](../../blite-architecture/SKILL.md) and follow it for the PRD. The artifact is `.bstack/<name>/design.md`.
3. **Verification.** Read [the verification skill](../../blite-checks/SKILL.md) and follow it for the PRD. The artifact is `checks.md` with its failing tests, pinned as the check SHA.
4. **Implement.** Give an `impl` worker `design.md`, the approved `index.md` with its 정책 section, the check SHA, and `checks.md`. The table and its tests stay as pinned: `git diff <check SHA> HEAD -- <test paths>` stays empty, and `checks.md` stays identical to its copy at the check SHA wherever the PRD folder sits. A worker that finds a check or the design wrong stops and reports.
5. **Clean up and open the PR.** An `impl` worker strips diff noise (debug output, dead code, comments that restate the code), reruns the checks, and leaves small ordered commits. Move the PRD with `git mv .bstack/<name> .bstack/archive/<name>` and commit. Push the branch and open a ready PR from this head: title `type(scope): subject`, body under 40 lines with `## Why`, `## What changed`, `## Verification`. Pin that head. The code is now final.
6. **Review and merge.** Run [Shipping](shipping.md). On `FAIL`, one `impl` worker finds why the findings were missed and fixes the change; on `STALE`, one rebases onto the current base. Either way it reruns the checks, and you send the new head to the same Shipping run with `bstack-run ask`. Stop at `MERGED` or at a blocker the user must decide. Rework at most twice; before a third, wait for the user's approval.

Work that is not in `checks.md` and needs doing later goes in the backlog, whether a reviewer or a worker found it. Do not add it to the PRD or `checks.md`, or expand the work to fix it. After `MERGED`, update the base branch, add these items to `.bstack/backlog.md` (start it from the [backlog template](../../blite-feature/references/template/backlog.md)), commit, and push. If the approved design or an in-scope check must change, or a contract conflict blocks the agreed work, ask the user. Append the answer verbatim to `request.md`, update the PRD, `design.md`, and `checks.md` where it affects them, fix the code, pin a new check SHA, and continue. A user decision needs no new PRD review.

**Reply:** what was built, each requirement with the evidence that passed it, the merge commit, and open decisions.
