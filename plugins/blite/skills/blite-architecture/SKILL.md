# 아키텍처 리뷰

목표는 요구사항을 이루는 구조를 처음부터 맞게 정하는 것이다. 구조가 틀리면 구현을 잘해도 덧댐이 쌓인다. 함수, 세부 타입, 작업 순서 같은 구현 방식은 정하지 않는다.

작업 크기에 맞춰 깊이를 정한다. 사용자와 이미 정한 것은 다시 묻지 않는다. 확인 방법(코드 추적, 변경 기록, 구조가 다른 안의 비교, 실행으로 전제 확인 등)은 아직 모르는 것에 맞게 고른다.

## 사용자와 정할 것

- **현재 구조.** 바뀌는 곳이 지금 어떻게 동작하고 어느 경로가 실제로 쓰이는가. 용어, 경로, 모듈 경계는 소스에서 확인한 뒤 쓴다. 요구사항과 현재 구현을 대조해 빠지거나 사라지는 동작을 드러낸다.
- **모듈 경계와 책임.** 각 모듈이 맡는 것과 맡지 않는 것.
- **상태 소유.** 상태마다 주인은 하나다. 다른 곳은 읽거나 주인에게 바꾸라고 요청한다. 둘 이상이 같은 상태를 쓰면 한쪽만 고친 규칙이 갈라진다.
- **데이터·이벤트 흐름.** 누가 만들고 누가 쓰는가. 클라이언트와 서버처럼 경계를 넘는 곳.
- **엔진과 라이브러리.** 엔진이나 라이브러리가 이미 제공하는 것을 다시 구현하지 않는가. 제공 기능을 쓰면서 그 위에 같은 일을 하는 자체 계산을 따로 두지 않는가.
- **재사용과 호환성.** 앱의 공용 부품과 이 기능 전용 코드를 구분해 무엇을 그대로 쓰는가. 저장 데이터와 공개 계약처럼 지켜야 할 호환.
- **영향 범위.** 같은 것을 읽고 쓰는 코드, 저장 데이터, 생성 자료, 문서, 도구. 이름 검색이 닿지 않는 곳까지.
- **파일.** 새로 만들 것, 고칠 것, 지울 것, 그대로 쓸 것을 레포 상대 경로로.

## 확인과 산출물

설계를 사용자에게 보여 주고 확인받는다. 사용자가 판단할 결정은 선택지와 그 영향을 함께 보여 준다. 확인받은 판을 design.md로 남기고, 무엇으로 확인했는지(소스 위치, 실행 결과)도 적는다.

확인은 보여 준 그 판에만 유효하다. 확인 뒤 설계가 바뀌면 바뀐 부분을 보여 주고 다시 확인받는다. 일부 결정에 답하면서 새 질문이나 대안을 낸 답은 확인이 아니다.
