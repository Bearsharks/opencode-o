# 승인된 PRD를 인계한다

`bstack_prd_start({name: "PRD 이름"})`으로 시작한다. 반환된 `folder`가 작업공간이다. 요청과 이후 합의를 이곳에 반영한다. 사용자가 결정을 알려주면 재진술에서 끝내지 말고 파일을 고쳐 이어간다.

- **`requirements.md`**: 누가 무엇을 하려는지, 기존 동작과 바뀔 규칙, 범위, 결정의 출처를 적는다. 실제 코드·자료에서 확인할 수 있는 내용은 직접 찾고, 관찰이 필요하면 허용된 격리 실험을 수행한다. 관찰 결과와 아직 실행하지 않은 검증을 구별한다. 필요한 관련 Markdown은 같은 폴더에 추가한다.
- **`criteria.md`**: 템플릿의 제목·앵커는 유지하고 `⟪작성⟫`을 채운다. 제품 가설과 기능 각각에 **성공 정의 / 검증 / 근거**를 쓴다. 근거는 *왜 이것이 성공인가(D)*와 *검증 통과가 어느 조건에서 왜 성공을 보장하는가(V)*로 구분한다. [검수 기준](references/rubric.md)을 사용한다. `index.md`는 도구가 구성한다.
- **해결할 공백이 있을 때**: [사용 가능한 메서드](references/methods.md)에서 필요한 것만 선택한다. 스스로 확인할 수 없는 결정·접근권만 `bstack_prd_wait({kind:"question",reason:"필요한 답"})`에 기록하고 사용자에게 묻는다. 사용자가 보류·중단을 요청하면 `kind:"hold"`를 사용한다. 둘 다 승인이 아니다.
- **작성 후** `bstack_review({})`를 호출한다. 도구가 실제 파일을 읽어 제품·기능 검수자에게 보낸다. `RESOLVE`나 초안 오류는 같은 폴더에서 고쳐 재제출한다. 일시 장애·권한 부족을 승인으로 바꾸지 않는다. **두 검수자의 `PASS`와 발행된 `artifact` 경로**가 있을 때만 완료를 보고한다.
