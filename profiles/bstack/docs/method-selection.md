# bstack-clarify 메서드 성공 기준: 무엇을 왜 이식하는가

**상태: 사용자 결정으로 아홉 메서드 확정.** 이 문서는 선택·검사 명세이며 실제 실행 성공을 대체하지 않는다. 기존 요약문 대신 고정 원본에서 이식한다.

| 구분 | 성공 정의 | 판정 방법 | 근거 |
|---|---|---|---|
| 기능 | 기획 스킬을 선택한 경우에만 제품 가설·기능의 성공 정의, 검증, 두 근거를 정리한다. 쟁점을 먼저 해소하고 준비된 후보를 독립 검수에 제출한다. 제품 구현은 스킬이 아닌 메인의 책임이다. | (1) 고정 원본·조사 대상 확인, (2) 이식 파일 전부를 원본 + 검토된 최소 패치와 대조, (3) 실제 호스트에서 스킬별 본문 로드와 사례별 검수·결과 확인. 세 판정은 별개다. | 스킬 등록, 원본 보존, 적절한 실행은 서로 다른 보장이다. 최종 답변의 자기보고는 독립 검수 기록을 대신할 수 없다. |

공통 원칙: 원본은 그대로 시작하고 “어느 칸을 위해 호출하고 무엇을 돌려받는가”는 중앙 흐름에 둔다. 파일명/메타데이터·도구 ID·권한·외부 인계처럼 **그대로 실행하면 실제로 충돌하는 부분만** 위치·이유·대체 동작과 함께 diff를 승인한다. 원본의 전제조건을 조용히 제거하거나 설명 전체를 한국어 단축본으로 바꾸는 것은 실패다. 원본이 가리키는 외부 스킬·도구도 실제 사용 분기별로 연결·대체·차단을 명시해야 한다. 디렉터리 해시 하나로 외부 의존성 해결까지 증명되지는 않는다.

## 2. 선택에 충분한 조사를 했는가?

판단 범위는 **현재 정의된 공백마다 맞는 방법이 있고 인접 방법과 구별되는가**이다. ECC 전체에서 최적임을 증명하는 것이 아니다. 기존 세 Runner 조사(병렬/반증 방식, ECC 도메인/제품 질문, pstack 측정·완료조건)에 더해 위의 고정 원본에서 입력, 실제 절차, 종료 조건, 호스트 의존성 및 라이선스를 대조했다. 아래는 선택하지 않은 근접 후보까지 추적할 수 있는 반대 근거다.

| 대조 후보(고정본) | 이번 선택에 미친 판단 |
|---|---|
| E `skills/intent-driven-development/SKILL.md` | 기존 스펙을 처음부터 다시 묻지 않고 관찰 가능한 AC로 보완하는 좋은 대안. 여기서는 행동–결과의 양방향 반례와 최소 확인을 직접 제공하는 pstack acceptance를 우선한다. 별도 AC 체계를 둘 필요는 없다. |
| E `commands/plan-prd.md`, `commands/prp-plan.md` | 문제 근거와 가설을 구분하는 데 참고했다. bstack-clarify도 PRD를 발행하지만 ECC의 명령 체인이나 구현 지침 전체를 이식하지는 않는다. |
| P `profiles/pstack/skills/how/SKILL.md`, `profiles/pstack/skills/why/SKILL.md` | 현재 동작과 결정 이력을 구별하는 근거. 첫 버전에서는 대상 사실을 읽는 것과 전체 조사 워크플로를 구분한다. 두 워크플로를 한 개의 짧은 `trace` 원본이라고 주장하지 않는다. 추가 도입은 별도 결정이다. |
| P `profiles/pstack/skills/benchmark-checklist/SKILL.md`, `profiles/pstack/skills/poteto-mode/playbooks/eval.md` | 수치의 유효성과 블라인드 평가에는 각각 별도 전제가 있다. 일반 `measurement` 스킬의 원본으로 합치지 않는다. 성능·모델 평가에서 실제 공백이 생기면 별도 메서드로 재검토한다. |
| E `skills/architecture-decision-records/SKILL.md` | context-and-decisions가 넘기는 ADR 절차를 확인했다. 용어 해석과 비가역적 결정 기록은 다른 책임이다. 이 프로필은 제품 저장소에 ADR을 쓰지 않는다. |

**후속 결정:** 이 절의 8개 자료는 1차 대조 목록이다. [당시 미채택 스킬 원문 13개 비교](alternative-review.md)에서 제안한 두 후보를 사용자가 채택하여 총 9개가 되었다. 기존 요약형 `trace`·`measurement`는 포함하지 않는다.

## 3. 재현 가능한 판정 명령

저장소 루트에서 Python 3와 Git으로 실행한다. 네트워크·모델 호출·설치는 필요 없다. 두 고정 커밋의 Git 객체가 로컬에 있어야 한다.

```sh
python3 profiles/bstack/docs/check-selection.py sources
python3 profiles/bstack/docs/check-selection.py ports
```

- `sources`: 명세의 9개 ID, 커밋별 tree/blob 해시, 인용 행 범위, 대조 후보 원문과 고지 파일을 확인한다. **조사가 재현 가능한가**의 판정이지 선택이 옳다는 자동 투표가 아니다.
- `ports`: 원본 전체 파일 + 공통 라이선스를 대상 스킬별로 대조한다. 플레이북 원문은 `SKILL.md`에 대응한다. 최소 변경이 있다면 `docs/port-exceptions/<ID>.patch`(기준 디렉터리 상대 `a/...`, `b/...` 경로) 및 같은 이름의 `.md`에 충돌 위치·이유·대체 동작을 남겨야 한다. 임시 원본에 패치를 재생해 실제 대상의 파일 집합·바이트와 같을 때만 통과한다. **미승인 대형 재작성도 패치로 포장할 수 있으므로 패치 내용과 이유는 사람이 승인한다.** 당장 이 검사를 녹색으로 만들기 위해 예외를 만들지 않는다.
- 어느 명령이든 `0`은 해당 범위 통과, `1`은 불일치/자료 누락이다. `ports` 통과도 OpenCode에서의 로딩이나 효과는 증명하지 않는다. 향후 실제 실행 기록으로 명확한 요청에서 도구 무호출, 모호한 요청에서 선택적 스킬 호출과 재판정, 관찰 근거가 없을 때 보류를 별도 검증한다. 모델이 매번 같은 판단을 할 것을 결정론적이라고 주장하지 않는다.
