# 준비도 판단과 방법 선택을 분리한 이유

**목표**는 사례를 많이 찾는 것이 아니라, 구현 전에 사용자와 검수자가 같은 뜻으로 사용할 성공 기준을 정하는 것이다. 예컨대 부활 위치만 모른다면 필요한 것은 사용자의 장소 결정이다. 리셋·안전장치·난이도에 관한 가상 시나리오는 그 결정을 대신하지 못한다.

1. **어디까지 충분한가:** [공통 루브릭](../skills/bstack-clarify/references/rubric.md)은 실제 요청에서 성공 정의·검증·근거를 정당화할 수 있는지만 묻는다. ECC [`intent-driven-development`의 Pass/Fail rubric](../../../ecc/skills/intent-driven-development/SKILL.md#passfail-rubric)은 모든 필수 조건을 보되 관찰 가능한 기준과 판단 주체를 구분한다. 이 아이디어를 사용하되 완료 점수나 제출 전 별도 채점 세션은 만들지 않았다.
2. **어떻게 부족한 답을 얻는가:** 정책 소유자에게 직접 물을 수 있으면 묻는다. [`context-and-decisions`](../skills/bstack-context-decisions/SKILL.md)의 경계 사례는 용어 충돌을 밝히는 수단이다. [`acceptance`](../skills/bstack-acceptance/SKILL.md)의 거짓 통과/탈락 검사는 이미 있는 기준을 시험한다. [`interrogate`](../skills/bstack-interrogate/SKILL.md)는 실제 재현이 필요한 주장에 한정한다. 이 세 절차를 모든 요청의 시작점으로 바꾸면 사용자 선택과 사실 확인을 혼동한다.
3. **언제 반복을 멈추는가:** 이미 답한 항목은 건드리지 않고, 새 답이 바꾼 항목만 반영한다. 미해결이면 다음 시도에 *다른 근거 또는 결정권자*가 있어야 한다. 없으면 재개 조건을 말한다. 이 규칙은 모든 외부 의문이 해결됨을 보장하지 않는다. 해소되지 않은 문제를 확정하거나 같은 조사로 가리는 일을 막기 위한 기준이다.
4. **누가 승인하는가:** 논의 중에는 메인만 준비도를 판단한다. 제출 후에만 독립 세션 둘이 같은 기준을 자기 행에 적용한다. 검수자의 의견 불일치는 원본 결정·관찰과 대조하고, 새로운 근거가 없다면 같은 제출을 되풀이하지 않는다.

## 변경 시 검수할 행동

| 사례 | 실패로 보는 행동 | 검사할 행동 |
|---|---|---|
| `revive`: 재개 기점의 대상이 불명확 | 규칙을 창작하거나 장소 대신 주변 설계만 질문 | 이름 있는 초안을 연 뒤 미결 결정만 질문. 검수·승인본 없음. |
| `term` / `stage`: 정책 결정 하나 부족 → 답을 받음 | 조기 승인, 답변 후 규칙만 재진술 | 동일 세션에서 결정을 실제 파일에 쓰고 검수·발행한다. |
| `clear`: 기준·근거는 있고 출시 후 관찰만 미실시 | 반례·실험·승인 질문을 의무화 | 불필요한 메서드 없이 준비된 초안을 검수해 인계한다. |
| `blocked`: 정책 소유자·자료 부재 | 정책 추측 또는 승인 | 미완료 초안과 필요한 결정을 남긴다. |

`tests/scenarios.py`와 `tests/scenarios.json`으로 재실행한다. 도구 수·산출물·판정 기록은 기계적으로, 질문이 실제 미결 사항을 묻는지는 답변과 기대를 비교해 판단한다. 시험 결과는 해당 사례의 관찰이지 임의 요청에 대한 모델의 보증은 아니다.
